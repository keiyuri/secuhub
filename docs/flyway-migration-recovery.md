# Flyway 다단계 DDL 마이그레이션 작성 원칙

## 배경 (역사적 기록)

과거 `V18__fix_tb_time_reg_date_type.sql`이 `ADD COLUMN` → `UPDATE` → `DROP COLUMN + CHANGE COLUMN`을
가드 없이 순차 실행하는 방식으로 작성되어, 연결 끊김 등으로 중간에 실패하면 `schema_history`에
실패가 기록되고 이후 모든 마이그레이션과 애플리케이션 기동이 막히는 문제가 있었다.

배포된 환경에서는 실패한 마이그레이션 파일을 고칠 수 없고(Flyway 체크섬 검증 — 이미 성공
적용된 파일을 고치면 checksum mismatch로 막힘), 뒤에 복구 마이그레이션을 추가해도 소용없다
(Flyway는 실패한 마이그레이션을 해결하기 전에는 그 뒤의 어떤 버전도 실행하지 않음).

이 문제의 원인이 된 `V18`을 포함해 `V1`~`V32`는 2026-09-03 시점에 아직 실제 운영 MariaDB에
한 번도 적용되지 않았음을 확인하고 단일 `V1__init_schema.sql`로 스쿼시했다(코드 리뷰 지적 —
사후 수정성 마이그레이션이 30개 가까이 누적된 상태로 첫 배포를 맞으면 이후 영구히 되돌릴 수
없다). 스쿼시는 32개 마이그레이션을 실제 MariaDB 10.11 컨테이너에 순서대로 적용한 뒤
`mysqldump`로 최종 스키마를 그대로 캡처해 새 `V1`으로 삼는 방식으로 검증했다(별도 컨테이너에
새 `V1`만 적용한 결과와 스키마가 바이트 단위로 동일함을 확인). 이 과정에서 원래 마이그레이션
체인 자체에 있던 버그 2건(V23의 컬럼 참조 순서 오류, V26의 ALGORITHM=INPLACE 강제)도 함께
드러나 해소됐다 — 새 `V1__init_schema.sql`의 파일 상단 주석에 상세 기록.

**이미 한 번이라도 배포된 환경이 생긴 뒤에는 이런 스쿼시를 다시 해서는 안 된다** — Flyway가
`schema_history`에 저장된 체크섬과 파일의 현재 체크섬을 비교하므로, 이미 적용된 환경에서는
파일을 한 글자만 바꿔도 시작 시 checksum mismatch로 막힌다.

## 재발 방지 원칙

새로 작성하는 다단계 DDL 마이그레이션은 반드시 **배포 전** 단계에서 `information_schema` 조건
확인 후 `DELIMITER`/프로시저로 감싸는 idempotent 가드를 적용한 상태로 최초 커밋해야 한다 —
한 번 배포된 뒤에는 파일을 고칠 수도, 뒤에 복구 마이그레이션을 붙일 수도 없기 때문이다.

## BASELINE(레거시) DB에 대한 자동 ALTER 금지 원칙 (2026-09-04 추가)

### 배경

로컬 개발 DB(`localhost:28031` = `192.168.0.26:28031`)는 Flyway 도입 이전부터 존재하던 레거시
스키마를 그대로 `baseline-on-migrate=true`로 베이스라인 잡은 환경이다 — `flyway_schema_history`의
V1 행이 `<< Flyway Baseline >>`(type=BASELINE)이라는 뜻은, V1의 `CREATE TABLE` 문이 실제로
한 번도 실행되지 않았다는 뜻이다. 게다가 이 DB는 여러 워크트리 세션과 별도 저장소
(GateControl/SR_Speed_Server)가 동시에 접속·수정하는 **공유** DB다.

V34(BASELINE 환경엔 시드 INSERT가 없다) → V36(BASELINE 환경엔 인덱스/컬럼이 없다) →
V37(BASELINE 환경엔 레거시 컬럼 타입이 남아있다) → V38(BASELINE 환경엔 `snd_raw` 컬럼이
없다)로 이어진 일련의 마이그레이션은 전부 "이 특정 공유 DB의 실측 상태를 사후에 보정한다"는
동일한 패턴이었다. 그런데 2026-09-04, V37이 이미 `success`로 기록된 뒤에도 실제 컬럼 타입이
다시 레거시 TINYINT로 돌아가 있는 드리프트가 재확인됐다(작업일지 0109) — 원인은 정확히 특정하지
못했지만, 이 DB를 동시에 건드리는 다른 세션/저장소가 있는 한 Flyway 이력에 success로 남아있다는
사실만으로는 실제 스키마 상태를 보장할 수 없다는 것을 보여준다. "실측 후 사후 보정 마이그레이션을
계속 追加한다"는 패턴 자체가 이런 공유·레거시 DB에서는 밑 빠진 독이 될 수 있다.

### 원칙

1. **새 자동 보정(auto-fix) 마이그레이션을 이런 공유/레거시 DB를 겨냥해 작성하지 않는다.**
   `V1` 행이 BASELINE 타입인 DB(=Flyway 이전부터 존재하던 레거시 스키마를 베이스라인 잡은 DB)에
   대한 컬럼 타입/누락 인덱스 보정은 원칙적으로 이 저장소의 Flyway 마이그레이션으로 자동화하지
   않는다 — 대신 DBA/운영자가 실측 후 수동으로 조치하고, 필요하면 이 문서에 조치 이력을 남긴다.
2. **꼭 자동 보정이 필요하다면(예: 앱 기동 자체를 막는 치명적 결함), 반드시 아래 가드로 BASELINE
   환경에서는 스스로를 건너뛰게 만든다** — "BASELINE 환경의 실제 상태를 알 수 없으니 손대지
   않는다"를 기본값으로 한다:

   ```sql
   -- V1이 BASELINE으로 기록된 환경(=레거시 스키마를 그대로 베이스라인 잡은 공유/구환경)인지 확인.
   -- 이런 환경은 이 마이그레이션 체인이 실제 스키마 상태를 보장할 수 없으므로 자동 ALTER를
   -- 건너뛴다 — 조치가 필요하면 DBA가 실측 후 수동으로 한다.
   SET @is_baseline_env = (
       SELECT COUNT(*) FROM flyway_schema_history
       WHERE version = '1' AND type = 'BASELINE'
   );
   SET @vNN_sql = IF(@is_baseline_env > 0,
       'DO 0',
       '<실제 ALTER/보정 문장>'
   );
   PREPARE vNN_stmt FROM @vNN_sql;
   EXECUTE vNN_stmt;
   DEALLOCATE PREPARE vNN_stmt;
   ```

3. **주기적으로 쌓인 실측 보정 마이그레이션은 정기적으로 다시 스쿼시한다.** V1~V32(2026-09-03)에
   이어 V33~V39(2026-09-04)도 같은 방식으로 새 V1에 흡수했다(신선한 스크래치 DB에 순서대로 전부
   적용 → `mysqldump --no-data --routines`로 결과를 그대로 캡처 → V1로 교체). 이 스쿼시는 아직
   운영 배포가 없는 동안에만 반복할 수 있다 — 한 번이라도 배포된 뒤에는 절대 금지(위 원칙 그대로).
