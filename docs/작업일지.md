### 커밋 1 — PacketDiffer 로직 수정 (`ce059a1`)

레거시 `ClsPacketAnalyzer.AnalyzePacketChanges`와 Kotlin `PacketDiffer.diff`를 바이트 단위로
대조해 2건의 동작 차이를 발견하고 수정했다:

- **모터 부하값(오프셋 70~71) 제외**: 레거시는 이 값이 자주 변동해 DB 쓰기가 급증하는 것을 막기
  위해 `operationStatusChanged` 판단에서 의도적으로 제외했는데, Kotlin은 포함하고 있어 변경
  감지 최적화 효과가 사라져 있었다. `changed(58,16)` → `changed(58,12) || changed(72,2)`로 수정.
- **Tail 체크섬(앞 2바이트) 제외**: 체크섬은 페이로드의 파생값이라 레거시는 비교 대상에서 제외하고
  고정 ETX 값(뒤 2바이트)만 비교했는데, Kotlin은 Tail 4바이트 전체를 비교하고 있었다. 수정 후
  회귀 테스트 4건 추가(총 7건 통과).

### 커밋 2 — SendControlJob/ReqStatusJob 및 부수 유틸리티 이식 (`cc75ed4`)

**게이트 제어 명령 전송 (`SendControlJob`, 레거시 `ClsQuartzJobSendControl` 대응)**
- `tb_data_snd`(미전송 큐)를 폴링해 `GateConnectionRegistry.sendToLane`으로 실제 전송.
- `sendToLane`이 액터 큐에 즉시 enqueue하고 반환하는 구조라, 레거시의 "타임아웃 이후에도 체인에
  남아있는 in-flight 전송" 추적(`_inFlightSendIds`, 5초 타임아웃 continuation 등)이 구조적으로
  불필요해짐 — `snd_id`별 5초 쿨다운 하나로 재전송 방지를 단순화.
- RESET류 명령 전송 성공 시 해당 게이트의 미해결 오류를 일괄 resolve 처리(`resolveYn='Y'`).
  레거시는 MOTOR/OPER/GATE 서브타입별로 다른 컬럼을 갱신했으나, 원본 SQL을 확보하지 못해
  정확한 컬럼 매핑을 추측하는 대신 "해당 게이트의 미해결 오류 전체 resolve"로 스코프를 좁혔다
  (코드 주석에 명시, 후속 작업 대상).

**게이트 상태 능동 조회 (`ReqStatusJob`, 레거시 `ClsQuartzJobReqStatus` 대응)**
- 커넥션별로 상태 조회 패킷을 만들어 전송. `tb_net_state` 갱신은 레거시와 달리 이 잡에서 하지 않고
  `DefaultGatePacketHandler`가 실제 `GATE_STATUS`(0x4D) 응답을 수신했을 때만 수행하도록 아키텍처가
  이미 분리되어 있어, 중복 갱신 로직을 추가하지 않았다.

**엔티티/스키마 매핑 보완**
- `DataSend.sndTypeCd`(`snd_type_cd`), `DataReceiveAnalysis.resolveUser`/`resolveDate`
  (`resolve_user`/`resolve_date`) — V1 마이그레이션 스키마에는 있었으나 엔티티 매핑이 누락돼 있던
  컬럼을 추가.

**부수 유틸리티**
- `IpMaskingUtil`(레거시 `RightIPMasking`/`LeftIPMasking` 대응): 로그용 IP 부분 마스킹.
- `ServerIpDetector`(레거시 `GetRealIpAddress`/`FindGetGatewayAddress` 대응): JVM 표준 API에는
  게이트웨이 주소 조회 기능이 없어, 활성·비가상 NIC의 사이트로컬(사설 대역) 주소를 우선하는
  휴리스틱으로 대체(한계를 코드에 명시). `ServerModeConfig`/`GateTcpServer`와의 실제 연동은
  범위 밖으로 남김.
- `LocationProperties`(`securance.location.*`)/`CloudProperties`(`securance.cloud.*`): 레거시
  ini `[LOCATION]`/`[CLOUD]` 섹션 대응 설정 스캐폴드만 추가. 레거시에서도 실사용처가 불분명했던
  항목이라 로직은 구현하지 않음.

**설정/등록**

  (기본 5초) 추가, `SchedulerConfiguration`에 두 잡의 staggered-start 트리거 등록

- Header의 Address(offset 6~18, 13바이트)를 전혀 채우지 않는다(0으로 남음).

기준으로 이 필드들을 전부 정확히 계산한다. 실기기가 이미 레거시 형식에 맞춰 동작 중이므로 어느

보이는 부분까지 의도적으로 동일하게 재현한다.

  - `buildModeChangeCommand(laneNo, controlType, timeDataUser?, timeDataSecu?)`: Object Code

같은 성격의 판단). 이관한 범위: **위치별 배치도 이미지 업로드 + 그 위에 그룹 아이콘 드래그 배치**만.
축소 근거:
1. 현재 스키마(`tb_gate_dtl`)에는 장비별 좌표 컬럼이 아예 없다 — 장비 아이콘 배치를 이관하려면
   스키마 확장이 선행되어야 하는데, 이는 이번 작업의 자연스러운 범위를 넘어선다.
2. 상위 "구역 지도"(위치들을 배치하는 최상위 계층)는 레거시에서도 `loc_x`/`loc_y`가 무엇을 기준으로
   그려지는지(상위 지도 이미지 자체가 어디서 오는지) 명확하지 않았고, 이번 이관의 실사용 목적
   ("이 위치에 어떤 그룹들이 있는지 한눈에 보기")에는 위치별 배치도만으로 충분하다고 판단했다.
3. WinForms `DoDragDrop`(네이티브 OS 드래그 소스 API)은 웹에 1:1 대응이 없다 — HTML5 Pointer
   Events(마우스 다운→이동→업 시 좌표 저장)로 동등한 사용자 경험을 재구현했다.

## 2026-08-06 — Phase 6 코드 리뷰 및 보안 수정

### 배경

Phase 6(#3 GateReset 리셋 실행, #5 SetupLocation 지도 좌표)에서 신규로 추가된 코드를 대상으로
전수 리뷰를 진행했다. 특히 이번 Phase에서 처음 등장한 두 가지 새로운 유형의 코드 — (1) AJAX
`fetch` 기반 좌표 저장, (2) 사용자 업로드 파일을 그대로 정적 서빙하는 경로 — 에서 실제 동작
결함과 보안 취약점을 발견해 모두 수정했다.

### 발견 및 수정

1. **[치명적] 좌표 저장 `fetch`가 CSRF 보호에 막혀 항상 실패**
   - `SecurityConfig`에 `csrf { disable() }`가 없어 Spring Security 기본 CSRF 보호가 켜져
     있는데, `location-map.html`의 그룹 마커 드래그 저장 `fetch(...)`는 CSRF 토큰을 싣지 않고
     있었다. Thymeleaf `<form>`은 `thymeleaf-extras-springsecurity6`가 hidden input을 자동
     주입해주지만 순수 JS `fetch`는 그 대상이 아니다 — 결과적으로 서버가 매 요청을 403으로
     거부했다.
   - 게다가 `fetch`는 4xx/5xx 응답을 reject하지 않으므로 기존 `.catch()`만으로는 이 실패를
     감지하지 못해, 사용자는 아무 에러 알림 없이 좌표가 조용히 저장되지 않는 상태를 겪었다.
   - 수정: `layout/dashboard-layout.html`에 `<meta name="_csrf">`/`<meta name="_csrf_header">`
     추가, `location-map.html`의 `fetch`가 이 값을 읽어 헤더에 실어 보내도록 수정, 응답
     `res.ok`를 직접 확인해 실패 시에도 알림이 뜨도록 개선.

2. **[높음] 업로드 파일 확장자 화이트리스트 부재 → 저장형 XSS 가능성**
   - `GateLocationService.uploadMap`이 저장 파일명의 확장자를 클라이언트가 보낸
     `originalFilename`에서 그대로 가져왔다. 유일한 검증인 `ImageIO.read` 성공 여부는, 유효한
     이미지 바이트 뒤에 HTML/스크립트를 이어붙인 폴리글롯 파일도 통과시킬 수 있어, `.html`/
     `.svg` 확장자로 저장된 뒤 `/loc-images/**` 정적 핸들러를 통해 그대로 실행될 위험이 있었다
     (게이트를 실제로 제어하는 관리 콘솔이라 영향도가 낮지 않음).
   - 수정: 확장자를 `png/jpg/jpeg/gif/bmp` 화이트리스트로 강제, 벗어나면 기존
     `IllegalArgumentException` 처리 경로(error flash)로 흡수.

3. **[중간] 업로드 용량 초과 시 500 에러 페이지 노출**
   - `spring.servlet.multipart.max-file-size`(10MB)를 넘기면 `MaxUploadSizeExceededException`이
     발생하는데 이를 잡는 핸들러가 없어, 다른 업로드 실패와 달리 친절한 한글 안내 없이 스프링
     기본 500 화이트라벨 페이지가 노출됐다.
   - 수정: `web/common/MultipartExceptionHandler.kt`(신규, `@ControllerAdvice`) 추가 — 예외를
     잡아 error flash 메시지로 Referer 화면에 되돌린다.

4. **[낮음] 이미지 판독 실패 시 고아 파일**
   - `file.transferTo(target)` 직후 `ImageIO.read(target)`이 실패하면(비이미지 업로드 등) 이미
     디스크에 쓰인 target 파일이 어디에도 참조되지 않은 채 남아 `data/loc-images`에 쓰레기로
     쌓였다.
   - 수정: 판독 실패 시 `target.delete()` 후 예외를 다시 던지도록 `try/catch`로 감쌈.

5. **[낮음] 파일시스템 쓰기와 DB 트랜잭션의 비원자성**
   - `uploadMap`은 `@Transactional`이지만 파일 삭제/쓰기는 DB 트랜잭션 롤백과 무관하게
     즉시 반영된다. 현재는 이 메서드가 트랜잭션의 마지막 단계라 위험이 낮지만, 향후 같은
     트랜잭션에 로직이 추가되면 롤백 시 파일 상태와 DB가 어긋날 수 있다.
   - 별도 리팩터링 대신, 이 위험을 코드 주석으로 명시해 다음 작업자가 인지하도록 했다.

### 검증

- `./gradlew.bat build` — 32 tasks, 실패 0(수정마다 재실행하며 확인).
- CSRF 헤더 전송, XSS 페이로드 업로드 차단, 대용량 업로드 시 플래시 메시지 등은 브라우저·
  MariaDB 연동 환경이 없어 실기 검증은 못했다 — 코드 경로상 정상 동작함을 리뷰로 확인.

## 2026-08-06 — Phase 7: #10 SR_F_ViewLog 구현

### 배경

계획서 4절에 착수 전 레거시 스펙 메모(`SR_F_ViewLog.cs`/`SR_C_MariaDB.SelectGateLog`)만 남기고

쓰는 통합 테이블 `tb_data_rcv_anal`이 그 대체재이기 때문이다. 그래서 새 테이블/엔티티를 만들지
않고 `tb_data_rcv_anal`을 원본으로 재사용하는 쪽으로 설계를 바꿔 구현했다(자체 판단, 사용자
확인 없이 진행 — Phase 5/6의 범위 축소 판단과 동일한 성격).

### 설계 및 구현

- **원본 테이블 재사용**: `DataReceiveAnalysisRepository`(#9와 동일)를 그대로 쓰고, ViewEvent와
  다른 화면으로 구분했다:
  - ViewEvent(`/reports/events`): 미해결 오류 추적 중심, `resolve_yn` 워크플로, PLM/STA 위주.
  - ViewLog(`/reports/logs`, 이번 구현): 정상(NOR) 통신까지 포함한 원시 로그 열람, 해결여부
    컬럼 없이 "발생일시/유형/IP/레인/설명"만 노출.
- **분류(log_cat) 대체**: 레거시는 `event_type` 코드(01=ACCESS, 08=PARKING, 10=DATA OBJECT,
  18=SYSTEM, 20=COMMUNICATION)로 `log_cat`을 매겼지만, 현재 스키마의 `tb_data_rcv_anal`에는
  이 원본 코드가 없다. 대신 이미 있는 `analType`(NOR/EVT/PLM/STA/ERR)을 유형 필터로 그대로
  노출했다 — 완전히 동일한 분류 재현은 스키마 확장이 선행돼야 하므로, "통신 로그를 필터링해
  조회한다"는 화면의 핵심 목적만 동등하게 제공하는 것으로 범위를 좁혔다.
- **설명(desc) 컬럼**: 레거시는 `TB_LOG_EVENT` 조인으로 사람이 읽을 메시지를 치환했는데, 그
  테이블이 없으므로 `tb_data_rcv_anal`의 desc_* 16개 컬럼 중 값이 있는 것만 이어붙이는
  `LogReportService.buildDescription`으로 대체했다.
- **빈 설명 행 제외**: 레거시 `SelectGateLog`가 빈 설명(`sDesc`) 행을 결과에서 뺐던 것과 동일하게,

- **조회기간**: 레거시와 동일하게 기본값 "전일~내일", 최대 3개월 제한(초과 시

- **엑셀 내보내기**: `ExcelExportService` 공용 컴포넌트를 재사용(#8/#9와 동일 패턴), 헤더는

`GATE_STATUS` 패킷 안에 로그 구간이 섞이지도 않는다.

### 지적사항 — `IsNotConnected` 미이식으로 물리 센서 단절이 온라인으로 잘못 표시됨

레거시 `SpeedServer.cs`(`case "4D":` 블록)는 `GATE_STATUS` 패킷을 받을 때마다 레인별로
`IsNotConnected`를 호출해 `TB_NET_STATE.dtl_state`를 갱신했다. 판단 기준은 레인 상태 블록
74바이트 중 레인번호(byte 0)·에러코드(byte 41)를 제외한 나머지 72바이트가 전부 0인지 여부 —
게이트가 레인 슬롯 자체는 계속 보고해도 물리 센서가 분리되면 이 나머지가 전부 0으로 온다.

신규 [DefaultGatePacketHandler](../securance-server/src/main/kotlin/kr/co/securance/secuhub/server/tcp/DefaultGatePacketHandler.kt)는
`net_state`(온라인 여부) 큐잉 대상을 "레인이 패킷에 유효하게 보고됐는지"(`PacketDiffer.laneNumbersOf`,
즉 레인번호 필드가 1~32 범위인지)만으로 판단하고 있었다 — `IsNotConnected`에 대응하는 센서 값
확인이 아예 없었다. 그 결과 물리 센서가 분리된 레인도 레인번호 바이트만 유효하면 계속
온라인으로 남아, 대시보드가 실제 배선 상태와 어긋날 수 있었다.

### 조치

- [PacketDiffer.isLaneConnected](../securance-protocol/src/main/kotlin/kr/co/securance/secuhub/protocol/PacketDiffer.kt)를
  추가해 `IsNotConnected`를 순수 함수로 포팅(반환 의미만 반전 — "연결 여부" 자체를 반환).
  판정 기준은 레거시와 동일: 나머지 72바이트 중 하나라도 0이 아니면 연결, 전부 0이고
  에러코드가 0 또는 3 이상이면 미연결, 전부 0이고 에러코드가 1·2면 연결. 블록이 패킷 범위를
  벗어나면(파싱 오류) 레거시와 동일하게 안전한 기본값인 "연결"로 처리한다.
- 기존에 private였던 `PacketDiffer.laneOffsetsOf`(레인 번호 → 오프셋 맵)를 `DefaultGatePacketHandler`가
  재사용할 수 있도록 public으로 전환.
- `DefaultGatePacketHandler`에서 레인 라우팅(`replaceLaneNumbers`, 제어 명령 대상 판단)과
  `net_state` 온라인 판단(`isLaneConnected` 결과 기준)을 분리했다 — 센서가 일시적으로 끊겼다고
  제어 라우팅 대상에서까지 빼면 안 되므로, 두 목적을 하나의 집합으로 섞지 않는다. 신규 온라인
  집합이 줄면(센서 단절 포함) 기존 "새로 나타난/사라진 레인만 큐잉" 최적화(위 리뷰들에서 이미
  도입됨)를 그대로 재사용해 오프라인 전이도 자동으로 큐잉되게 했다.

### 배경

### 지적사항 1(critical) — `application.yml` DB 자격증명 하드코딩

`spring.datasource.*` 기본값이 실접속 가능한 원격 DB(`192.168.0.91:28030` / `dba`/`securance`)로

### 지적사항 2(high) — `V3__add_timezone.sql` 부분 실패 후 재실행 불가

MariaDB DDL은 트랜잭션 롤백이 보장되지 않아, 기존 `tb_time`을 `tb_time_legacy_backup`으로
이름 변경한 뒤 새 `tb_time`을 만드는 도중 마이그레이션이 부분 실패하면(연결 끊김 등), 재실행 시
"새 tb_time"과 "tb_time_legacy_backup"이 동시에 존재하는 상태가 될 수 있었다. 이 상태에서 기존
로직을 그대로 재실행하면 새로 만든 tb_time을 레거시로 오인해 다시 백업 이름으로 옮기려다
`tb_time_legacy_backup` 이름 충돌로 실패하고, 배포가 영구 차단될 수 있었다.

[V3__add_timezone.sql](../securance-domain/src/main/resources/db/migration/V3__add_timezone.sql)의
백업 프로시저에 "이미 새 스키마(`timezone_hex_data` 컬럼 존재)면 건드리지 않음" +
"백업 테이블이 이미 있으면 다시 RENAME하지 않음" 조건을 추가하고, `CREATE TABLE`을
`CREATE TABLE IF NOT EXISTS`로 바꿔 각 단계를 개별적으로 idempotent하게 만들었다 — 어느
지점에서 재실행하든 최종 상태가 "새 스키마의 tb_time 1개(+레거시가 있었다면 백업 1개)"로 수렴한다.

`@DisallowConcurrentExecution`은 JVM 하나 안에서만 유효하고 Quartz도 RAMJobStore라, 롤링

## 2026.08.07 0005 실데이터 재검증 — 센서 미연결(errorCode=3) 레인 포함 패킷으로 `isLaneConnected` 확인

### 배경

0003 항목에서 검증한 372바이트 4레인 SR-1400 캡처는 4개 레인이 전부 정상(`isLaneConnected=true`)

### 검증 방법

프로젝트 코드를 수정하지 않고, [PacketDiffer.kt](../securance-protocol/src/main/kotlin/kr/co/securance/secuhub/protocol/PacketDiffer.kt)의

### 결과

## 2026.08.07 0007 `GateLogService`(패킷 재조립→DB 저장) + 수신 로그 조회 화면 신규 구현

### 배경

0006에서 남겨둔 후속 과제("`GateLogService`와 조회 화면은 범위 밖")를 이어서 진행해 달라는
요청. `GATE_LOG`(0x61) 로그 엔트리 디코더(`LogEventCodec`)까지는 이미 있었으므로, 이번에는

② `securance-web`에서 그 데이터를 조회하는 화면을 새로 만들었다.

### DB — `tb_gate_log` 신설

레거시 `TB_DATA_RCV_LOG`(+`TB_LOG_EVENT` 조인)와 개념은 유사하지만, `TB_LOG_EVENT`(코드→메시지

### 멱등성 설계(자연키 UNIQUE + find-or-create)

`GateDbWriteQueue`는 타임아웃 이후 버려둔 실행이 뒤늦게 완료되면 같은 작업이 두 번 실행될 수
있다고 명시하고, 그래서 `execute`는 항상 멱등(UPSERT 등)이어야 한다고 요구한다
([GateDbWriteQueue.kt](../securance-server/src/main/kotlin/kr/co/securance/secuhub/server/db/GateDbWriteQueue.kt)
클래스 KDoc "주의(멱등성)"). `tb_net_state`처럼 자연스러운 복합키 UPSERT 대상이 없는 append-only
로그 테이블이라, (게이트 IP, 레인, 이벤트 발생시각, 이벤트유형, 코드, 에러코드, 기능코드) 조합을
자연키로 삼아 저장 직전 `existsBy...` 조회로 중복을 막는 find-or-create 패턴을 적용했다

DB에도 같은 조합으로 UNIQUE 제약을 걸어 이중 방어한다. 트레이드오프: 이벤트 시각이 BCD라 초 단위
정밀도뿐이라, 같은 초에 완전히 동일한 조합의 이벤트가 실제로 두 번 발생하면 드물게 하나로 합쳐질

`GATE_STATUS`와 달리 `GATE_LOG`는 문서상 DataInfo(45바이트) 구간이 없는 일반 프레임 구조

## 2026.08.07 0008 — GATE_LOG 패킷 레이아웃 가정 정정(레거시 재검증)

### 배경

0007 항목에서 "GATE_LOG(0x61)는 DataInfo 없는 독립 패킷(Header+Data+Tail)"이라는 가정을
명시적으로 미검증 상태로 남겨뒀다. 사용자 요청으로 레거시 `SR_Speed_Client`/`SR_Speed_Server`
(C#, `D:/workspace/vstudio/Maintenance/GateControl`)를 다시 분석해 이 가정을 재검증했다.

### 발견 사항

레거시 `SpeedServer.cs`(1011~1064행)와 `ClsPacketAnalyzer.cs`를 확인한 결과, 실제 동작은
가정과 달랐다:

- 레거시는 `objCode`와 무관하게 **매 수신 패킷**에서 로그 유무를 판단한다(`changeState.IsLogChanged`).
  즉 독립된 "GATE_LOG 오브젝트 코드 패킷"이라는 개념 자체가 레거시에는 없다.
- 로그 엔트리는 실제로 `GATE_STATUS`(0x4D) 패킷 **끝에 이어 붙어** 온다:
  `Header(27)+DataInfo(45)+Status(laneCnt*74)+Log(logCnt*36)+Tail(4)`.
- `logCnt`는 헤더의 `DATA_COUNT` 필드(오프셋 23~24)에서 읽고, 로그 시작 오프셋은
  `Header+DataInfo+(laneCnt*74)`다 — Header 직후가 아니다.
- 로그 엔트리의 레인 번호는 엔트리 자체의 6번째 바이트(Module Number)에서 읽는다
  (`bLog[6]`) — 이는 `GateLog_protocol_20260728.docx`(레거시 저장소 최상위, 텍스트 추출로
  확인)가 정의하는 36바이트 엔트리 구조의 "Module Number(Gate Lane Number)" 필드와 정확히
  일치한다. 다만 이 문서는 엔트리 36바이트 "자체"의 필드 구조만 규정할 뿐, 이를 감싼 **패킷
  프레이밍**은 규정하지 않는다 — 프레이밍 근거는 레거시 구현이 유일하다.

즉, 이전 구현은 GATE_LOG를 objectCode `0x61`로 명시 전송하는 패킷에만 반응하도록
`DefaultGatePacketHandler`에 분기를 추가했는데, 실제 하드웨어가 레거시와 동일하게 동작한다면
그런 패킷은 오지 않고 로그는 `GATE_STATUS`(0x4D) 패킷 안에 묻혀 그대로 버려지고 있었을
가능성이 크다 — 신규 저장 기능이 사실상 동작하지 않는 상태였을 수 있다.

### 조치

- [GateLogService.kt](../securance-server/src/main/kotlin/kr/co/securance/secuhub/server/tcp/GateLogService.kt)에

  디코딩/저장할 수 있도록 일반화했다(기존 `saveIfAbsent`/멱등성 로직은 공유).
- [DefaultGatePacketHandler.kt](../securance-server/src/main/kotlin/kr/co/securance/secuhub/server/tcp/DefaultGatePacketHandler.kt)의
  `GATE_STATUS` 분기에서 `packet.dataCount > 0`이면 레거시와 동일한 오프셋 공식으로 로그 구간을
  계산해 `handleEmbedded`를 호출하도록 추가했다.
- 문서상 정의된 독립 `GATE_LOG`(0x61) ObjectCode 경로(`handle`)는 신형 펌웨어가 실제로 그렇게
  보낼 가능성을 완전히 배제할 수 없어 하위 호환/향후 대비용으로 그대로 남겨뒀다 — 두 경로 모두
  같은 저장 로직을 공유하므로 유지 비용이 낮다.
- `GateLogServiceTest`에 `handleEmbedded` 검증 테스트 추가, `DefaultGatePacketHandlerTest`에
  `GATE_STATUS` 패킷 끝에 이어붙은 로그가 올바른 오프셋으로 위임되는지 확인하는 회귀 테스트 추가.
